## O que é

Assistente de IA (RAG) para o IFRS Campus Canoas. Um widget de chat injetado sobre um clone da página oficial do campus responde perguntas de estudantes a partir de uma base vetorial de documentos do site (páginas e PDFs). Pensado para deploy serverless no Vercel.

## Comandos

Ambiente (Windows, PowerShell):
```powershell
.venv\Scripts\activate
pip install -r requirements-dev.txt
```
`requirements.txt` é SÓ a produção (o que a função serverless no Vercel instala; o Vercel resolve com `uv lock`, então dependência de dev ali quebra o deploy). `requirements-dev.txt` inclui a produção e soma ingestão e avaliação.

Rodar o app local (Flask). A porta 5000 costuma estar ocupada por um túnel SSH na máquina de dev, use outra via `PORT`:
```powershell
$env:PORT=5050; .venv\Scripts\python.exe -m ui.app
```
Acesse `http://127.0.0.1:5050`. Rode sempre como módulo (`-m ui.app`) a partir da raiz, nunca `python ui/app.py`, por causa dos imports de pacote (`rag.`, `ui.`).

Popular / atualizar a base vetorial (pipeline completa: crawler com detecção de mudança, parsers, chunker, ingest, snapshot):
```powershell
$env:ANOS_VALIDOS="2023,2024,2025,2026"; .venv\Scripts\python.exe pipelines\ingest_pipeline.py
```
O modo default é incremental por `source_hash` (ver Arquitetura): o crawler varre o site inteiro, mas só o que é novo ou mudou segue para parse (LLM) e embed. Flags de exceção, com override via env (string `"True"`/`"False"`): `REPARSE=True` ignora os hashes e reprocessa tudo que já existe (replace geral, sem zerar o index); `REINGEST=True` zera o index e reingere do zero; `INCLUDE_SCANNED=True` volta a baixar/processar PDFs escaneados (imagem, sem texto), que o default pula (ver Arquitetura). `ANOS_VALIDOS` também aceita override via env (CSV, ex: `ANOS_VALIDOS=2026`; o default deriva da data: ano anterior + corrente, para não congelar um intervalo que apodrece na virada do ano).

Gerar o `index.html` que o app serve (snapshot com a faixa de aviso e o widget já injetados); também roda no fim da pipeline de ingestão:
```powershell
.venv\Scripts\python.exe -m ui.clone_page
```

Rodar a bateria de avaliação (eval), em dois passos independentes (estratégia detalhada na seção "Bateria de testes"):
```powershell
# 1) coletar: roda o agente N vezes por caso e salva os traces em eval/runs/coleta.jsonl.
#    Caro (chama o LLM); rode só quando o comportamento do agente muda (prompt, modelo, base).
$env:EVAL_N="5"; .venv\Scripts\python.exe -m eval.run_eval coletar
#    re-coletar só alguns casos (merge: preserva a coleta dos demais):
$env:EVAL_IDS="biblioteca-horario,diretor-geral-campus"; .venv\Scripts\python.exe -m eval.run_eval coletar

# 2) validar: aplica as 7 fases sobre a coleta salva e GERA o relatório. Barato, instantâneo; itere à vontade.
.venv\Scripts\python.exe -m eval.run_eval validar
```
O `validar` sempre regenera `eval/runs/relatorio.md` e `eval/runs/ultimo_resumo.txt` (detalhe com IC por caso), e imprime o relatório. O `relatorio.md` é a PROVA canônica para olhos externos: traz a config da coleta (modelo, versão/versões de prompt com contagem, período), o placar com IC de Wilson 95% em TODAS as fases, o caveat de que as Fases 5/6 (juiz) são sinal e não régua, a classificação de cada falha (bug real vs flake de 1 run vs gap de base vs artefato de métrica) e uma tabela por caso (25 casos x fases). Toda mudança no formato da prova vai no `gerar_relatorio`, para valer também nos próximos runs. As fases objetivas (1-4, 7) são checadas por regra. As semânticas (5 geração, 6 comportamento) usam um juiz LLM com switch `EVAL_JUDGE`:
- `claude` (default, zero custo de API): o `validar` escreve as tarefas em `eval/runs/juiz_tarefas.jsonl`; o próprio Claude Code julga via subagente e grava `juiz_vereditos.jsonl`; re-rode `validar` para ver 5/6 no relatório.
- `gemini` (inline): `$env:EVAL_JUDGE="gemini"; .venv\Scripts\python.exe -m eval.run_eval validar` julga chamando o Gemini e já preenche os vereditos; o relatório sai completo num comando só. Qualquer valor diferente de `gemini` cai no modo claude (o script não chama LLM, só consome os vereditos existentes).

`vercel dev` NÃO funciona no Windows nativo (bug do `@vercel/python`: gera path com `\U` não escapado em `vc_init_dev.py`). Para teste fiel do empacotamento Vercel, use WSL ou faça deploy real (Linux). Para validar a lógica, use o Flask local acima.

## Arquitetura

Duas metades independentes que só se encontram na base vetorial Upstash:

**1. Ingestão (offline: na máquina do dev ou no GitHub Actions semanal)** - `pipelines/ingest_pipeline.py`
Modular desde jul/2026: `ingest_pipeline.py` é só o ORQUESTRADOR (mesmo entrypoint de sempre); cada fase vive no seu módulo em `pipelines/` (`config.py` = flags/constantes/caminhos/clientes/sessão HTTP, `urls.py` = classificação e transformação de URLs, `dates.py` = inferência de `published_at`, `crawler.py`, `parser_html.py`, `parser_pdf.py`, `parser_sheets.py`, `chunker.py` (inclui `classify_campus_scope`), `ingest.py`), com o grafo de imports acíclico (todos dependem de `config`, nunca o contrário). Pipeline sequencial: crawler varre `ifrs.edu.br/canoas`, parser HTML e parser PDF extraem texto (as grades de horário aSc são lidas por VISÃO - gemini-2.5-flash multimodal, um chunk por professor -, pois a extração de texto embaralha a tabela 2D, ver "Retrieval: ... grade por visão"; datas de publicação inferidas por LLM a partir do próprio documento), parser de planilhas baixa Google Sheets publicados (links `docs.google.com/spreadsheets` achados no site) como CSV e estrutura em frases via LLM (`type: "sheet"` no metadata, UMA frase por registro), chunker fatia em pedaços (planilha e grade são fatiadas UM REGISTRO POR CHUNK via `por_linha=True`, ver "Retrieval: ... grão por registro"), ingest embeda com Gemini e faz upsert no Upstash, e o snapshot regenera o `ui/index.html` (via `clone_page`) que o app serve estático. Os dados intermediários (`data/raw/`, `data/parsed/`, `data/chunks/`) estão no `.gitignore` e não trafegam pelo Git; só o Upstash (nuvem) é compartilhado entre máquinas.

Detecção de mudança (`source_hash`, `pipelines/hashing.py`): o crawler carrega do Upstash o estado por URL (`source_hash` + ids dos chunks), baixa cada recurso e hasheia o conteúdo bruto ANTES de qualquer parse (HTML: texto extraído do `main`, estável entre fetches; PDF: bytes; planilha: CSV). Hash igual = inalterada, nem chega ao parser (zero LLM, zero embed); hash diferente ou URL nova = segue no fluxo, e a mudada tem os chunks antigos deletados no ingest (replace). Cada chunk tem id determinístico `url#i` e grava o `source_hash` no metadata, fechando o ciclo para o run seguinte. A base é 100% `url#i` desde jul/2026: os 4.966 ids numéricos legados (da ingestão original, 43% da base) foram migrados por `pipelines/migrations/migra_2026_07_ids_legados.py` (migração versionada, com backup do mapeamento em `backups/` e modo `reverter`; só a identidade mudou, vetor e metadata intactos). Efeito colateral aceito: traces de telemetria anteriores à migração guardam ids legados e o harvest não os hidrata mais. Dedup por conteúdo entre URLs (`_duplicata`): se o `source_hash` de um recurso já pertence a OUTRA URL (na base ou vista antes no mesmo run), o crawler pula (nem parseia nem ingere), tratando como duplicata; a 1ª URL de cada conteúdo é a dona. É o caso do re-upload `-1` do WordPress (mesmo arquivo byte-a-byte, URL nova), que inflava o contexto do retrieval com o documento repetido. Hashear o HTML cru não funciona: toda página carrega um nonce anti-bot (`__uzdbm_1`, Radware) que muda a cada request; por isso o hash do HTML é do texto extraído, com a extração fatorada em `extract_page_content` e compartilhada entre crawler e parser. O mesmo Radware responde uma PÁGINA DE DESAFIO (captcha, HTTP 200) na requisição sem cookie, no lugar do conteúdo; por isso o crawler usa uma sessão HTTP persistente (`SESSION`/`fetch` em `pipelines/config.py`) que guarda os cookies `__uzm*` e, ao detectar o desafio, repete na mesma sessão (aí passa, sem precisar de navegador/JS). Sem isso cada requisição vira uma 1ª visita e recebe o captcha, e a varredura colapsa (o alcance caía de ~2442 para ~2 URLs). O parser usa `raise_for_status()`, então página com erro HTTP real (ex: 451) é pulada sem sobrescrever o conteúdo bom que já está na base. O `run_ingest` só deleta o antigo de uma URL mudada que produziu chunk novo (`urls_mudadas & por_url`): se o parse do conteúdo novo falha, o antigo é preservado (nunca deleta sem repor).

PDFs escaneados (imagem, sem texto extraível) nunca geram chunk (o chunker pula `is_scanned`), então não têm `source_hash` na base e, sem tratamento, seriam re-baixados a cada run. O parser registra os escaneados em `data/parsed/pdfs_scanned.json` (versionado no Git, junto com `pdfs_format_errors.json`, para semear o CI e evitar que ele re-baixe os ~1359 escaneados a cada run; o resto de `data/parsed/` segue gitignored) e, com `INCLUDE_SCANNED=False` (default), o crawler pula o download dos já registrados. O registro se autopopula (um PDF é baixado uma vez para ser identificado como escaneado); numa máquina nova ele se refaz sozinho. Quando houver OCR/pixelrag, `INCLUDE_SCANNED=True` volta a processá-los.

Job periódico de ingestão: o GitHub Actions (`.github/workflows/ingest.yml`) roda o ingest incremental toda segunda 06:00 UTC (mais gatilho manual `workflow_dispatch`), atualiza o Upstash e commita o snapshot de volta (dispara o redeploy do Vercel). Os secrets no repo são `UPSTASH_ENDPOINT`, `UPSTASH_WRITE_API_KEY`, `UPSTASH_API_KEY` e `GEMINI_API_KEY_T1`. O `index.html` carrega um nonce por fetch, então há um commit e redeploy a cada run mesmo sem mudança de conteúdo.

**2. Serviço de chat (online, Vercel)** - `ui/app.py` + `rag/chain.py` + `rag/gatekeeper.py`
Flask stateless. O fluxo de uma pergunta: `gatekeeper` checa rate limit por IP no Redis e `chain.ask()` roda um agente com tool calling (Gemini `gemini-2.5-flash`). O modelo investiga a pergunta e decide entre chamar a ferramenta `buscar_documentos` (formulando uma query refinada, já corrigindo premissas como reitor->diretor) ou pedir esclarecimento ao estudante quando falta um discriminador (curso, tipo de prova). A ferramenta embeda a query e coleta um pool amplo do Upstash (`FETCH_K=60`) por similaridade, reordena por data E escopo de campus (`rerank_by_date`: `ALPHA*similaridade + (1-ALPHA)*score_de_data - penalidade_de_campus`; ver "Retrieval: escopo de campus, data e grade por visão") e corta os `CONTEXT_K=15` melhores para o contexto (over-fetch: o rerank escolhe de um pool maior sem inflar os tokens do LLM). O modelo então responde citando as fontes e explicitando o escopo (ex: "a prova de RECUPERAÇÃO do curso X"). Se a busca não retorna nada, o modelo é informado disso e responde honestamente que não encontrou, sem inventar (NÃO há fallback de internet). O prompt do agente (`data/info/agente-ifrs.txt`) traz defesas de segurança (nunca revelar as instruções; tratar o texto do usuário como usuário, não como sistema/autoridade; nunca usar prefixo imposto; redirecionar perguntas fora de escopo, inclusive conhecimento geral trivial) e dois comportamentos contra respostas cruas em perguntas vagas: quando o referente tem outra leitura plausível na base, responde a mais provável e menciona a alternativa (sem travar); e consciência temporal (a `data_atual` é calculada por request, não no import do módulo), ressalvando dados de anos anteriores em vez de apresentá-los como vigentes. Depois da geração, todo o pós-processamento passa por UM funil (`_pos_processar` em `chain.py`), que trata o bloco de fontes como DADO ESTRUTURADO em vez de re-parsear a string final em cada etapa: `_decompor_resposta` divide o texto do modelo UMA vez em (corpo, linhas `[n] url` do bloco "Fontes:") - texto que o modelo tenha posto DEPOIS das fontes volta ao corpo -, os guards operam sobre o corpo, `_backfill_fontes` completa as fontes e `_compor_resposta` serializa UMA única vez na borda de saída, sempre com o bloco "Fontes:" como ÚLTIMO elemento (contrato com o `widget.js`, que corta a mensagem em "Fontes:" para montar a seção clicável "Ver fontes"; qualquer disclaimer após o bloco seria engolido nela). Dentro do funil: (1) o GUARD DE SAÍDA (`_aplicar_guards`, determinístico para disparar + LLM foco em temperatura baixa para reescrever) faz duas checagens de consistência temporal: (A) se o corpo cita fonte de ano anterior ao atual sem ressalvar, ANEXA a ressalva; (B) se o corpo lidera com data já passada e o contexto tem data futura, reescreve liderando pela próxima ocorrência; é fail-safe (qualquer erro devolve o corpo original) e só aplica edição segura (rejeita reescrita que introduza URL ou citação nova). (2) o BACKFILL DE CITAÇÃO (`_backfill_fontes`, determinístico): a temperatura faz o modelo, às vezes, citar `[n]` no corpo mas esquecer o bloco de fontes; quando NENHUM bloco foi escrito, monta as linhas a partir do mapa `{n: url}` da última busca, na ordem de citação; nunca inventa fonte (`[n]` fora do mapa é ignorado) nem substitui bloco que o modelo escreveu. Fecha o caso "citou mas não linkou" (medido: 9/9 respostas que citam `[n]` passam a ter o bloco); resíduo é a resposta que não cita `[n]` nenhum (nada a linkar). A refatoração de jul/2026 (das 3 funções de string-parsing para o funil estruturado) foi validada com 16/16 casos byte-idênticos ao comportamento anterior. Logging: o `chain.py` fala por `logging` (nível DEBUG para o dump de retrieval, que contém a pergunta do usuário e por isso NÃO vai ao log de produção; WARNING para falhas de guard/rate-limit); o `ui.app` local liga DEBUG no pacote `rag`, o serverless não configura nada e só WARNING+ chega ao log da plataforma. A temperatura da geração vem de `AGENT_TEMP` (env, default 0.7).

Telemetria (opcional, `rag/telemetry.py`): cada turno do `/chat` é registrado no Langfuse no MESMO schema da coleta do eval (via `registro_de_trace` em `chain.py`), carimbado com a versão viva do prompt (`PROMPT_VERSAO`), sendo uma extensão da coleta por outra versão (mergeável pelo `prompt_versao`). Payload leve: guarda os ids dos chunks (`url#i`), não o texto cru; `eval/harvest_producao.py` puxa os traces e reconstrói o texto via `index.fetch(ids)` no Upstash, gerando `coleta_producao.jsonl` no formato do eval para curadoria (perguntas reais viram candidatas a caso de golden). Sem as chaves `LANGFUSE_*` a telemetria é no-op (local, eval e o Vercel sem chaves seguem funcionando); toda falha de telemetria é engolida, e o `/chat` trata erro do `ask` (500 limpo e registrado). Cada turno também leva um `user_id` (id anônimo por dispositivo, gerado no `widget.js` via `crypto.randomUUID` e guardado no `localStorage`) e um `session_id` (por carregamento de página, mesma vida do histórico); viram os campos Users/Sessions do Langfuse, dando um "quem" pseudônimo sem IP nem PII (evita o problema de NAT do wifi do campus, onde muitos alunos compartilham um IP).

### Retrieval: escopo de campus, data e grade por visão

O retrieval aplica três refinamentos além da similaridade crua: escopo de campus, data do documento e leitura das grades de horário por visão. Os casos de regressão correspondentes vivem no golden set marcados com `origem: "producao"`.

- **Escopo de campus, no RERANK (não na query)**: a base é toda do Campus Canoas, mas contém docs INSTITUCIONAIS do IFRS (multi-campus, ex: o "PDI IFRS 2024-2028") que dominam a similaridade e enterram a resposta certa (a query "salas dos professores prédio" trazia 28/30 chunks do PDI). Duas peças: (a) `FETCH_K=60` (pool grande o bastante para o doc certo de Canoas, que fica além do top-30 quando o institucional domina a similaridade crua, entrar no pool); (b) penalidade no rerank `ALPHA*sim + (1-ALPHA)*date_score - CAMPUS_PENALTY`, com `CAMPUS_PENALTY=0.35` para chunks `campus_scope=="outro"` (ausência = neutro 0), valor calibrado para tirar o PDI do contexto sem margem apertada. O escopo age no rerank, não na query, pois ancorar a query ao campus (`f"{query} IFRS Campus Canoas"`) infla editais institucionais e enterra a resposta em queries de professor. O `campus_scope` é atribuído no ingest por `classify_campus_scope` (ALTA PRECISÃO, para não expulsar doc de Canoas): tagueia "outro" só (a) fora do `/canoas/` E (b) com marcador institucional explícito (título "PDI"/"Plano de Desenvolvimento Institucional" ou >=4 campi do IFRS citados). NUNCA tagueia doc sob `/canoas/` (Canoas-específico mesmo citando a rede - senão o relatório CPA de Canoas virava "outro"). Hoje "outro" = o PDI (Drive, 269 chunks) + planos de ação IFRS institucionais (no `/site/`, não `/canoas/`). Além da penalidade, um CAP DURO `CAMPUS_OUTRO_MAX=0` (em `build_context`) EXPULSA do contexto todo chunk `campus_scope=="outro"`: a penalidade só REBAIXAVA o institucional, que ainda sobrava no top-15 e vazava (ex: "Torre Norte" do PDI aparecia nas salas dos professores); com o cap, nenhum institucional entra no contexto (a base é toda de Canoas, o institucional não responde daqui). Limite conhecido (ACEITO como erro aberto desde jul/2026): o doc-nível é grosso, então uma pergunta legitimamente institucional (reitor/PDI) ou que precise de uma seção ESPECÍFICA de Canoas DENTRO do PDI (o Quadro 5.3 de vagas planejadas, a infraestrutura 6.3) fica sem contexto, porque o cap expulsa o PDI inteiro. Houve um "refino por chunk" (`refinar_campus_scope`) que liberava essas seções, mas foi REMOVIDO em jul/2026 (ver "Soluções removidas"): tinha um só consumidor vivo (o Quadro 5.3 para vagas) e um bug de fronteira. Hoje o escopo de campus é SÓ doc-nível (`classify_campus_scope`) + cap, e o PDI está 100% fora do contexto. Consequência positiva: o vazamento do "611 de Bento" e a projeção-como-oferta somem por construção (o PDI nunca é recuperado). Consequência aberta: `total-vagas-campus` não tem no contexto o quadro de vagas do PDI (ver "Comportamento atual").
- **Data do documento (`get_published_at`)**: lê o ano do PRÓPRIO documento primeiro. Ordem: nome do arquivo (`extract_date_from_filename`, só para arquivos reais `.pdf/.docx/...`, NUNCA o slug de uma página HTML, que traz ano de evento futuro) -> conteúdo (LLM, ~1000 chars: 500 do início + 500 do fim) -> pasta `/YYYY/MM/` da URL (data de UPLOAD) só como fallback. O `_date_score` tem piso 0 (doc antigo fica neutro, nunca negativo).
- **Grade de horários por VISÃO / pixelrag** (`structure_schedule_vision`, `parse_pdf`): a grade aSc TimeTables é tabela 2D que a extração de texto embaralha (célula transborda a linha, coluna funde). Detecção em `is_schedule_pdf` por 3 redes (qualquer uma dispara): assinatura "aSc TimeTables" no conteúdo, OU título "Horários_", OU rede estrutural (>=3 dias da semana por TOKEN via `\b(Seg|Ter|...|Segunda|Terça|...)\b`, NÃO substring - senão "Ter" casava "Território", "Qui" casava "Aqui" e disparava a visão à toa; mais o marcador "criado:" e >=3 horários HH:MM). Cada página é renderizada (`get_pixmap` dpi 200, teto `max_pages=30`) e lida pelo gemini-2.5-flash (multimodal), que agrupa POR PROFESSOR. GATE anti-alucinação: horários/salas emitidos têm que existir no raw da página, senão a página é descartada (suspeita). `published_at` = ano do raw ("Horário criado:DD/MM/AAAA"). O chunker emite UM chunk por professor (`chunk_document(..., por_linha=True)`), não o splitter por tamanho, para o recall por professor não re-densificar. **Os marcadores `is_schedule=True` e `schedule_source` (visao/visao_parcial/fallback_texto) são PERSISTIDOS no metadata do Upstash** (só nos chunks de grade; ausentes nos demais para não inchar o metadata), tornando as grades auditáveis/filtráveis na base e sinalizando grade incompleta ou degradada - o que o texto do chunk sozinho não revela (uma grade parcial parece completa, só com menos professores). Truncagem (>`max_pages`) ou página pulada/descartada marca `visao_parcial`, então a incompletude fica VISÍVEL, não silenciosa. O conjunto na base = exatamente as grades linkadas na página oficial `ensino/horarios-das-aulas/` (10 do semestre 2026/2).
- **Grão por registro no chunk (planilhas e grades)** (`chunk_document(..., por_linha=True)`): quando um documento é uma LISTA DE REGISTROS independentes (uma planilha de atendimento com um professor por linha, uma grade com um professor por linha), ele é fatiado UM REGISTRO POR CHUNK, não pelo splitter por tamanho. Motivo (medido jul/2026): o splitter por tamanho empacotava ~20 professores num chunk de 4000 chars, e uma consulta a UM registro ("contato do professor X") disputava dentro do blocão, então o dado certo não chegava ao contexto (o email do professor chegava em só 5/25 casos testados na planilha de atendimento; com um chunk por linha, 25/25). O grão do chunk tem que casar com o grão do registro: como cada linha é um fato auto-contido (nome + sala + horário + email), o chunk por linha casa fortíssimo com a query da pessoa e ela é recuperada de forma confiável. Efeito colateral positivo: a desambiguação de homônimo (2 Igors, 2 Simones) emerge sozinha, pois o retrieval passa a trazer TODAS as pessoas do nome pedido, e o modelo as lista (sem precisar de regra no prompt). Regra de roteamento: usa-se `por_linha` quando a estrutura é lista de registros consultados um a um; prosa (regulamento, notícia, PPC) segue no splitter por tamanho. Aplicado no ingest (`chunker.py`: sheets sempre `por_linha=True`; grades via `is_schedule`) e migrado na base pela `pipelines/migrations/migra_2026_07_sheets_por_linha.py` (5 planilhas, 11 -> 314 chunks, com backup e `reverter`). GAP CONHECIDO: o **calendário NÃO entrou** neste tratamento (achado jul/2026, medido). O `por_linha` só está ligado ao `is_schedule`, não ao `is_calendar`, então mesmo o calendário estruturado (um evento por linha do `structure_calendar_text`) é fatiado por TAMANHO, empacotando eventos. Pior: 44 chunks de calendário na base são CRUS (grade de dias "Dom Seg Ter Qua 1 2 3...", 215 linhas por blocão) porque não passaram pelo gate `is_calendar_pdf` (calendários antigos/resoluções puxados pela re-run de range grande) - esses viram ruído. Fix pendente: (a) `parse_pdf` marcar `is_calendar=True` no ramo estruturado + `chunker` ligar `por_linha` para ele (SÓ o estruturado; por_linha num calendário cru vira lixo linha-a-linha); (b) limpar/gate os calendários crus antigos. A medir antes de aplicar.

Observabilidade de parsing: `run_pdf_parser` grava `data/parsed/pdfs_parse_report.json` a cada run (gitignored), com números + motivos de NÃO-entrada (escaneado, erro de formato, PII barrado, erro de download/parse) e a quebra por estruturação (vaga/grade/calendário/normal), COM amostras de URL. ### Servidor sem estado (decisão central)

O servidor NÃO guarda histórico de conversa, sessão, nem cookie. O histórico vive no cliente (`ui/widget.js`, variável em memória) e é enviado inteiro no corpo de cada `POST /chat`. O servidor sanitiza e aplica tetos anti-abuso (`sanitize_history` limita quantidade e tamanho do histórico; `MAX_QUERY_CHARS` limita a query; `check_global_budget` limita o volume diário) e repassa ao `ask`. Isso é o que torna o app compatível com o serverless do Vercel (instâncias efêmeras que não compartilham memória). Ao recarregar a página o histórico zera de propósito (vive em memória, não em `localStorage`), para contexto antigo não poluir uma nova conversa. O `localStorage` guarda só um id anônimo de dispositivo para a telemetria (`user_id`), que persiste no F5 mas NÃO repopula o histórico. O contexto multi-turno funciona durante a sessão ativa porque o array em memória acumula e vai junto em cada chamada.

### Página servida estaticamente

A rota `/` serve o `ui/index.html` já pronto (via `send_from_directory`); o app não busca o IFRS ao vivo nem cacheia em runtime (filesystem read-only do Vercel). O snapshot é montado offline por `ui/clone_page.py` (`build_page`: busca o HTML do IFRS, injeta a faixa de aviso `ALERT_BANNER` de ambiente não oficial e o `widget.js`) e regenerado na fase final da pipeline de ingestão, depois commitado. Assim a página só muda quando a base muda, e nenhum usuário paga o custo do fetch ao vivo.

### Separação de chaves Upstash

O Vector tem dois tokens, controlados por variável de ambiente distinta:
- `UPSTASH_API_KEY` (read-only): usado pelo `chain.py` em produção (só consulta). É o único Vector token cadastrado no Vercel.
- `UPSTASH_WRITE_API_KEY` (read+write): usado pela ingestão (`ingest_pipeline.py`). Fica só na máquina local, NUNCA no Vercel.

O Redis (`UPSTASH_REDIS_*`) usa o token padrão com escrita, pois o rate limiter incrementa contador a cada request. Read-only não serve ali.

### Embeddings

`gemini-embedding-001`, 3072 dimensões, similaridade cosine. O index Upstash precisa ser criado com esses parâmetros. Os scores do Upstash são normalizados em 0 a 1 (no antigo Qdrant iam de -1 a 1); o `min_score=0.60` em `chain.py` pode precisar de ajuste fino observando scores reais.

## Deploy (Vercel)

Entrypoint em `api/index.py` (reexpõe `from ui.app import app`); o preset Flask do Vercel resolve o app sozinho. `vercel.json` define `maxDuration: 60` para a função (folga para a chamada LLM e o loop de tool calling). Cadastrar no painel do Vercel as variáveis: `UPSTASH_API_KEY` (read-only), `UPSTASH_ENDPOINT`, `UPSTASH_REDIS_API_KEY`, `UPSTASH_REDIS_ENDPOINT`, `GEMINI_API_KEY_T1`. NÃO cadastrar `UPSTASH_WRITE_API_KEY`.

Não inventou, mas foi incompleto e desatualizado. A regra de ENUMERAÇÃO do prompt manda admitir incompletude, mas não dá cobertura. Solução em duas peças (padrão de mercado: metadata extraction no ingest + self-query/auto-retrieval no serving):
   (a) **Classificar cada DOCUMENTO num conjunto FECHADO de gêneros** (gênero, NÃO assunto: "oficina" é assunto dentro de notícia/edital) no ingest, pegando carona na chamada LLM que já infere `published_at` (pedir `{ano, tipo}` no mesmo call = custo marginal ~zero; backfill one-off dos ~3,7k docs em flash-lite = centavos). Distribuição MEDIDA (jul/2026, heurística de URL/título sobre 3.754 docs): noticia 36,6%, edital 29,2%, normativo 9,5%, pagina_institucional 8,9%, relatorio_plano 1,0%, planilha/calendario/grade/ppc ~0,6%, outro 14,2% - e o grosso do "outro" é URL opaca do Drive que um classificador por CONTEÚDO resolve (estimativa real do resíduo: um dígito %). Governança da taxonomia: "outro" é válvula de escape MONITORADA; se crescer ou aglomerar um tipo coerente, promove-se um gênero novo e re-classifica só o resíduo. A taxonomia não precisa nascer completa, precisa nascer auditável. O valor do `tipo` vai ALÉM da enumeração: (i) perguntas que nomeiam o gênero ("quais editais de bolsa?"; editais+normativos = 39% do corpus); (ii) RECÊNCIA POR GÊNERO - gêneros têm meia-vida diferente (edital/notícia envelhecem, normativo/PPC duram), e é isso que permite penalizar idade no rerank sem enterrar regulamento válido, o fix da classe do `salas-professores` (edital de 2019 vencendo página atual); (iii) distinguir "oferta atual" (edital do ano) de "projeção/histórico" (relatório/plano), o gap do gold do `total-vagas` (item 6); (iv) guard temporal calibrado por gênero; (v) auditoria da base e do harvest por gênero/ano.
   (b) **Modo enumeração no serving**: detectar intenção de agregação ("quais/todas/liste/quantas") e responder por CONJUNTO COMPLETO, não top-k. Núcleo determinístico: filtro de metadado por **`ano`** (o escopador robusto; `tipo` só refina QUANDO a pergunta o nomeia - o assunto "oficina" vive em VÁRIOS gêneros: notícias, editais de bolsista, páginas de projetos) com topK alto (o subconjunto de um ano é menor que o teto, então vem inteiro), e o match do termo ("oficina") feito NO CÓDIGO, client-side, sobre esse conjunto - sem GLOB, sem campo normalizado, sem índice novo. O modelo recebe a lista completa com a instrução de FORMATAR/deduplicar/marcar o que já passou (não de "achar"), fechando também o vazamento de geração. Por que não a busca vetorial: medido em jul/2026, a enumeração via vetor vaza em 3 pontos - (1) a formulação da query muda tudo ("quais oficinas tem" pôs 4/5 alvos no pool com rank 0; "oficinas do campus" pôs 0/5, pois a query genérica fica mais perto de páginas SOBRE oficinas-conceito que das notícias individuais, dominadas pelo próprio assunto); (2) um ponto de query não cobre N vizinhanças semânticas dispersas (mesmo na melhor formulação, só 3/5 entraram no top-15); (3) o modelo resume seletivamente em vez de inventariar. Fase 2 (só se a fase 1 não bastar): extrair a entidade evento (`{nome, data, status}`) no ingest. Nota de latência: é a única técnica de enumeração que não adiciona chamadas de LLM (gargalo medido: LLM = 72% do tempo, retrieval = 17%).
   (c) **Índice HÍBRIDO (denso+BM25): evolução separada, com GATILHO, não é o fix da enumeração.** O Upstash Vector suporta índice híbrido, mas o tipo é definido na criação (exige índice novo + migração dos 11,6k vetores + re-projetar o rerank, pois `ALPHA*score` e `MIN_SCORE=0.60` assumem escala cosine, + re-coleta completa do eval). O que ele compraria: robustez a termo exato que embedding erra (nome de professor, sigla TADS/PIBEN, número de edital, código de sala) e menos sensibilidade à formulação da query. O que NÃO resolve: os abertos atuais (salas = recência; total-vagas = fonte ausente; vazamento de geração da enumeração) - e o placar F3 já está em 95%, então o ganho hoje é prospectivo, não fecha falha medida. Redundância assumida: se o híbrido chegar, uma query só-esparsa ("oficina") + filtro + topK alto substitui o match client-side da enumeração. GATILHO de adoção: o harvest da telemetria mostrar perguntas reais falhando por termo exato, OU uma mexida no rerank já planejada (ex: recência por gênero) que pague a recalibração de uma vez.

Arquitetura / linhas de falha em escala (mapeadas jul/2026, pendentes de auditoria): o formato comum é o do bug do chunking das planilhas (fechado): UMA decisão de design numa camada, aplicada globalmente, que degrada em silêncio uma CLASSE inteira de perguntas. 1. **Grão de chunk ad-hoc por tipo**: não há decisão principiada de grão; é hardcoded (sheet e grade = por-linha; resto = por tamanho). Irmãos latentes do bug das planilhas: o CALENDÁRIO (linha-por-evento, ainda fatiado por tamanho) e páginas HTML que são LISTAS (equipe/horários, diretórios). Auditar cada tipo perguntando "isto é lista de registros?" e medir lookup-de-um + enumeração antes de aplicar.
2. **Retrieval martelo-único (vetor top-k)**: toda query vira embedding -> top-k por similaridade. Classes estruturalmente mal servidas: enumeração (precisa do CONJUNTO; já documentada acima), match EXATO (nome, sigla, nº de edital, código de sala, que embedding erra), contagem ("quantos") e multi-hop. Fix decidido para enumeração = generalização item 7; para match exato, o gatilho do híbrido (item 7c). Testar com baterias de ground-truth de conjunto e de termo exato.
3. **Teto duro CONTEXT_K=15 / FETCH_K=60**: resposta que precisa de >15 trechos é truncada por construção e apresentada como completa; doc além do rank 60 nunca entra no pool. Testar com perguntas cujo gold exige N>15.
4. **Query de busca estocástica (temp 0.7)**: a MESMA pergunta vira queries diferentes por run -> retrieval diferente -> resposta flaky (foi o mecanismo do "para que assunto" e da variação do total-vagas). Já descrito acima como "variação estocástica"; o teste estrutural é medir a VARIÂNCIA do contexto recuperado run-a-run no golden (quantificar a flakiness, hoje anedótica).
5. **`published_at` = um único ano inferido + recência só como peso**: (a) inferência de ano errada rebaixa/infla o doc em TODA query temporal, sem nenhuma auditoria da acurácia da inferência (veneno silencioso no ranking); (b) recência não sobrepõe similaridade (o resíduo das salas: edital 2019 de alta similaridade vence página atual); (c) sem granularidade de semestre (ver Próximos passos). Auditoria barata: amostrar docs e comparar ano inferido vs ano real, medindo taxa de erro.
6. **Sem modelo de entidade**: pessoa/curso/setor são só texto no chunk; homônimos (2 Igors, N Simones), variantes ("Cerezer"/"Maffini Cerezer") e typos da fonte ("Neubeger") são resolvidos no sorteio do retrieval + LLM. O caso Simone/Gustavo foi tratado no SINTOMA (chunking por-linha); a raiz (lookup por entidade canônica sobre índice estruturado) segue aberta. Testar com bateria de homônimos e variantes.
7. **Degradação silenciosa da base**: "nunca deleta sem repor" protege contra perda, mas um doc que falha o parse REPETIDAMENTE fica congelado numa versão antiga para sempre, invisível (ex: os ~18 PDFs do Drive com rate limit); e não há NENHUMA asserção de sanidade pós-run (contagem de chunks não colapsou, docs-chave presentes) entre "pipeline rodou" e "base está boa". Auditar docs cujo source_hash nunca atualiza + adicionar asserções ao fim do pipeline.
8. **Eval não cobre ingestão nem a base viva**: o `validar` roda sobre a coleta SALVA, então mudança de base/ingestão não é pega por regressão automática (o fix do chunking precisou de scripts ad-hoc). Falta um modo que re-execute retrieval contra a base viva (ex: asserção "o gold_url chega ao contexto" pós-ingestão).

### Bateria de testes (estratégia de avaliação)

Detalhamento do item 1. Princípio central: **simular o pipeline real** (a pergunta entra, o agente investiga, formula a query, busca no Upstash e responde) e aplicar a medição **onde ela se encaixa**. Não usar query fixa nem forçar determinismo: o pipeline passa pelo LLM (temperatura 0.7), então cada caso roda **N vezes** e reporta-se a **taxa** (ex: o doc correto chegou ao contexto em 4/5 execuções), que é a estabilidade real do sistema. Reportar incerteza (IC) porque a amostra é pequena.

Validações-alvo (o que se quer responder por caso):
1. investigou o suficiente? (trajetória: tomou a ação certa antes de responder)
2. criou a query certa pro Upstash? (formulação: corrigiu premissa reitor->diretor, incluiu ano/discriminador)
3. o RAG retornou os documentos corretos? (retrieval)
4. a resposta final fez sentido? (geração)
5. a resposta realmente existe na base? (answerability)
6. acréscimos: recusa apropriada (não alucinar quando ausente; perguntar quando ambíguo), segurança (jailbreak/fora de escopo), consciência temporal (ressalvar dado antigo), citação de fontes.

Eixo de medição (o que decide a técnica; NÃO é "determinismo", é objetivo vs semântico):
- **Objetivo** (checagem por regra sobre a execução real, sem LLM-juiz): docs retornados contêm o correto? (`gold_url`/`answer_span` no contexto real; Hit@k, Recall@k, MRR); a resposta existe na base? (varredura textual, independe da execução, separa falha de retrieval de ausência real); a query gerada tem o discriminador esperado? (regex); a ação tomada = a esperada? (chamou a tool vs respondeu direto); citação válida? (fontes citadas dentro das recuperadas).
- **Semântico** (LLM-as-judge; ainda A VALIDAR contra rótulos humanos em PT-BR antes de tratar como régua): fidelidade (não inventou), relevância e correção da resposta; recusa apropriada; ressalva temporal; resistência a jailbreak.

**Campos do caso.** Golden set único em `eval/golden_set.json`; cada caso reúne: pergunta + paraphrases, `tipo`, `acao_esperada`, `criterios_query` (deve/não deve conter), `gold_urls`, `answer_spans`, `existe_na_base`, `resposta_esperada` e `notas`. O histórico de conversa NÃO é campo do caso: é artefato de runtime, gerado ao encadear execuções (nunca uma resposta fixada no gabarito). As `paraphrases` são reformulações da mesma pergunta (mesma intenção, léxico diferente) para medir invariância à forma; quando o comportamento independe do referente, elas podem variar o próprio discriminador (ex: o caso `curso-inexistente` varia o nome do curso falso).

**Vocabulário de `acao_esperada`** (a decisão da Fase 1):
- `buscar`: chama `buscar_documentos` e responde.
- `corrigir_e_buscar`: corrige uma premissa errada do aluno e então busca (ex: reitor->diretor; curso que não existe -> curso real).
- `perguntar`: pede esclarecimento antes de buscar, oferecendo as opções conhecidas quando possível (ex: "atendimento de qual setor?"; "temos bolsa de monitoria, extensão...; qual?").
- `responder_direto`: responde sem retrieval quando é apropriado responder (saudação, meta-pergunta sobre o assistente).
- `recusar`: não entrega o conteúdo pedido. Dois gatilhos com tons distintos: jailbreak/prompt injection -> recusa firme (não vaza o prompt, não sai do papel); fora de escopo -> redireciona educado ("só ajudo com assuntos do Campus Canoas"). Fronteira com `responder_direto`: ambos dispensam retrieval; o que decide é se o agente DEVE responder o conteúdo.

`acao_esperada` pode ser uma **lista** quando mais de uma ação é aceitável (ex: `mensalidade-curso` aceita corrigir_e_buscar OU responder_direto - responder direto que é gratuito também serve; `bolsa-vaga` aceita perguntar OU buscar - listar todas as bolsas também serve). A Fase 1 passa se a decisão real (buscar/não-buscar) casar com qualquer uma das aceitas; o acerto do conteúdo em si cabe às fases 5/6.

**Turno único vs multi-turno.** Por padrão cada caso é de turno único e mede um movimento do agente. Um fluxo de esclarecimento (pergunta vaga -> agente pede o discriminador -> estudante responde -> agente responde) decompõe-se em dois casos independentes e complementares: um caso `perguntar` (mede se o agente pediu esclarecimento e se pediu bem) e um caso `buscar` já específico (mede retrieval e resposta final). Esse padrão já está no golden set: `atendimento-vago` é o "turno 1" e `biblioteca-horario`/`atendimento-igor` são "turnos 2" resolvidos. Nesses casos `resposta_esperada` descreve o output do turno (a pergunta de volta, com os discriminadores certos) e não se mede fidelidade (Fase 5), e sim comportamento (Fase 6). O multi-turno de verdade (roteiro `turnos_usuario`, com fusão de contexto: o turno 2 chega como fragmento "da biblioteca" que só vira query colado ao turno anterior) fica FORA do escopo atual por decisão; ele só acrescentaria o teste da fusão, que os dois casos independentes não exercitam.

**Padrões de comportamento a cobrir** (Fase 6):
- consciência temporal: gold que depende da data atual (início do próximo semestre, rematrícula do semestre vigente, "festa" sem edição do ano corrente, PIT antigo) exige manutenção ou regra dinâmica no avaliador; o gold reflete a referência da data em que foi curado.
- não-alucinar (`existe_na_base: false`): quando o dado não existe na base, admitir a lacuna e orientar, sem inventar (ex: qual sistema envia as horas complementares - o procedimento existe, a ferramenta concreta não).
- perguntar-com-opções e recusa (jailbreak / fora de escopo) conforme o vocabulário acima.

**Curadoria do gold (não-circular).** O gabarito é definido por CONTEÚDO, nunca a partir do que o `ask` recupera. Método: varrer TODA a base (`index.range`) nos três tipos (`html`, `pdf` e `sheet` - dado estruturado como horário de atendimento vive em planilha), achar o fato por varredura textual, confirmar no chunk e validar que cada `gold_url` casa EXATAMENTE com um `source_url` existente (senão o retrieval falha por typo). A busca vetorial serve só para DESCOBRIR candidatos, não para definir o gold. A `resposta_esperada` é a referência do fato correto, NÃO um gabarito literal: o sistema costuma responder muito além dela (a Fase 5 mede fidelidade e correção, não igualdade textual). Validar o gold rodando o pipeline real (`ask`) N vezes é parte do processo (foi assim que se achou, por exemplo, um documento faltando no gold do auxílio). Lição: checar a data da fonte antes de afirmar (uma página de 2016 apontou um sistema já descontinuado).

### Achados atuais da bateria

A bateria das 7 fases está implementada e roda em dois passos (`coletar`/`validar`); a metodologia está na seção "Bateria de testes". Placar vigente (coleta jul/2026, 30 casos, 695 execuções, versões de prompt mistas por atualização modular; Fases 5/6 = SINAL, juiz não calibrado): Fase 1 decisão 97%, Fase 2 query 100%, Fase 3 retrieval doc 95% / span 94% (MRR 0.70), Fase 5 fidelidade 98% / relevância 100% / correção 99%, Fase 6 comportamento 97%, Fase 7 citação 100% (todos com IC de Wilson no `relatorio.md`). **Caveat de integridade dos vereditos (achado jul/2026):** as Fases 5/6 do relatório vigente vêm dos vereditos do juiz salvos em `juiz_vereditos.jsonl`, e esses vereditos estão STALE para 29 dos 30 casos: foram gravados numa coleta anterior, com encoding quebrado (mojibake nos `input`) e índices de `run` de um n menor, então NÃO casam com a coleta atual (n=10) pela chave `caso+input+run`; o `_agg_fases56` agrega por `case_id` do próprio veredito e por isso o relatório PARECE completo, mas os números 5/6 desses casos não refletem os runs atuais. Só `total-vagas-campus` foi re-julgado limpo (UTF-8, runs atuais) nesta rodada. Antes de tratar 5/6 como régua é obrigatório um re-julgamento LIMPO da coleta inteira (purgar `juiz_vereditos.jsonl` e re-julgar os 695 numa passada só). As Fases objetivas (1-4, 7) são recomputadas da coleta a cada `validar` e não têm esse problema.
